Advisor Chat Console

Chat workflow only. Four phases. Phase 1 is the ask.

Engineering managers Advisor + Admin Phase 1 = build now ▶ Open prototype

01 Problem

  • 49% of chats got zero advisor reply, ever.
  • Open chats grew 47% Jun→Jul; volume grew 17%.
  • SLA measures first response only — "ok, will check" passes it.
  • Chats are rarely closed; we have no reliable closure signal today.
Root cause: advisors are rewarded for replying, never asked to finish.

03 Principles

P1Two clocks, not one — reply speed and closure are separate failures.
P2Status is derived, never declared. No dropdowns.
P3A reply is not a resolution. Only Close or "Not on me" clears the plate.
P4Priority states its reason, not just a colour.
P5Closure is the success metric. First response is a warning signal only.
P6Start from the dashboard, not the inbox.
P7Admin sees the same model, aggregated per agent. One definition.
P8Observe before intervening. Phase 1 admin is read-only.

04 Definitions

Status — derived

StatusRule

Action pendingAdvisor sent last and (flagged or holding reply)
Open sessionAdvisor sent last, nothing flagged — or a closed chat the client reopened
ClosedDisposition recorded
  • Automated messages never count as the last human message.

Reopening a closed chat

StepBehaviour
Client writes on a closed chatChat reopens automatically
Where it landsOpen session — not New. It is an existing session resuming, not a new chat.
Prior dispositionKept as history. Never overwritten.
ClocksBoth restart from the reopen.
Markingreopened tag on the row; banner in the chat naming the earlier disposition.
  • A reopened chat is itself a signal — it may mean the earlier closure was premature.

Ownership — primary / secondary

  • Every chat has a primary owner; some also carry a secondary advisor.
  • Shown as a facet, not a tab and not a switch — tabs carry state, chips carry ownership.
  • Chips: All / Primary / Secondary, counted within the active tab. Default All.
  • Rows carry a 2ND tag; the chat header and context panel name the other advisor.
  • Rationale: a hard switch hides half the book behind a control the advisor may never flip — the exact failure this product exists to prevent.

Two clocks

ClockTargetCounts
First response12 hoursBusiness hours only — 09:00–20:00, Saturdays excluded. The clock pauses 20:00→09:00.
Resolution / close48 hoursFlat for every chat. No category or tier variation.
  • Both targets are flat — not per tier, not per category.
  • First response catches silence. Resolution catches drift.

Action flag

TriggerResult
Plain reply→ Open session
☐ Requires my action→ Action pending
Holding reply detected→ Action pending + in-chat banner
  • Holding reply = last advisor message is filler only ("ok", "will check", "noted"). Fixed phrase list, not NLP.
  • Aging does not reset on an action-flagged reply.
  • Exit: Close, or "Not on me".

Agent at risk — admin highlight

No score. An agent is highlighted if they hold even one at-risk chat.

// a chat is At Risk on either hard condition chat_at_risk = not_closed_in_time age > 48h close target OR no_response_sent zero agent reply AND waiting > 12 business hours agent_at_risk = count(chat_at_risk) > 0
ConditionTestShown as
Chat not closedChat age exceeds the 48h close target"2 past close target"
Response not sentNo agent message at all, and waiting exceeds 12 business hours"3 no response sent"
  • Same definition drives the chat's At Risk band and the agent's highlight — one rule, two altitudes.
  • Computed per agent, not stored. Not a performance rating.
  • Widget shows the breakdown, not just a count, so the admin knows which condition fired.

Phase 1Triage & Respond ▶ Prototype

Advisor

  • Status tiles: Action pending · New chats · Open session · Open tasks. Each opens that filtered list.
  • At risk widget — priority + reason + close-by.
  • Chat tabs: All · New chats · Open session · Action pending. Sorted by priority.
  • Ownership facet: All / Primary / Secondary chips, plus a 2ND tag on secondary rows. Defaults to All so nothing is hidden.
  • Row shows: client, tier, band, reason, time on plate, close by.
  • Reply + ☐ Requires my action.
  • On-me banner with Not on me and Close inline.
  • Close → disposition: Query Resolved · Task Completed · No Action Needed · Escalated · Duplicate. Comment required on last two.
  • Holding-reply closure allowed, but flagged to audit.
  • Context panel: customer type, both ETAs, documents, past conversations.

Admin — two widgets on the existing dashboard

  • Existing dashboard widgets are unchanged. Two are added.
  • Open Chats widget — total, split into response pending and waiting for closure.
  • Agents at risk widget — agents with at-risk chats and their open item count.
  • Clicking either → the existing agent grid. That screen is unchanged.
That is the entire admin scope for Phase 1: two widgets and a link to a screen that already exists. Everything deeper is Phase 2.

Acceptance

  • A reply never clears ownership. Only Close or Not on me does.
  • Action-flagged reply does not reset aging.
  • Every priority row shows a reason.
  • Every tile and row lands on a correctly filtered destination.
  • Status is not settable by hand anywhere.
  • Admin counts reconcile exactly with advisor counts.
  • Open chats split adds up: response pending + waiting for closure = total open.
  • Both admin widgets link to the existing agent grid, which is not modified.

Metrics

  • Chats with zero reply: 49% → <5%
  • Median open → closed, by category
  • % closed with a disposition
Phase 2Admin acts · Closure is earned

Admin — from watching to acting

  • Drill agent → their chats → individual chat, with action pending marked per chat.
  • Admin chat filters: unanswered · at risk · action pending · blocked from closure.
  • Nudge — lands in the agent's Action pending. Logged, visible to both sides.
  • Reassign — first-response clock restarts, the 48h close clock does not.
  • Escalate — on second breach, actionable by someone other than the blocked agent.
  • Admin sees holding-reply closures flagged for review.

Advisor — closure accountability

  • Task-gated closure — no close while any linked task is OPEN. Enforced server-side, not just the button.
  • Task aging — ships with the gate, never after.
  • MOM as a task type, created from a completed meeting.
  • Meetings today on the advisor dashboard.
  • Day ladder: D1 amber + digest · D2 orange + one push · D3+ red + repeating. Never per message.

Acceptance

  • Close rejected by API when an open task exists.
  • Open task past threshold surfaces to admin.
  • Every nudge is attributable and visible to the agent.
  • No per-message notifications.
Phase 3Tune & assure quality
  • Category risk computed live from breach rates.
  • Threshold calibration against observed agent capacity.
  • Audit queue workflow — review holding-reply and premature closures.
  • Reopen-rate tracking as a closure-quality signal.
  • Per-segment SLA config — targets editable without a deploy.
  • Admin saved views and alerting on breach conditions.
Phase 4Scale & intelligence
  • Load-balanced routing — assign by capacity, not by hand.
  • Agent trend lines — performance over time, not just today.
  • Capacity planning and peak-season forecasting.
  • Coaching insights — recurring failure patterns per agent.
  • Bulk admin actions across an agent's book.

06 Out of scope

  • Milestone / case-outcome tracking.
  • Client-facing status tracker.
  • Self-serve bot.
  • Per-topic granularity inside one chat — status is chat-level.

07 Open questions

  • Sundays? The first-response clock excludes Saturdays and pauses 20:00–09:00. Sunday handling was not stated — assume excluded?
  • Third at-risk condition? Two are defined — chat not closed, response not sent. A third was mentioned but not named.
  • Status derived on read, or materialised with a recompute job?
  • Holding-reply phrase list — config or code? Prefer config.
  • Cost of the server-side close gate on a hot endpoint? Phase 2
  • Can category risk be computed live, or nightly job? Phase 3
  • Is client tier reliably present on every chat today?
  • Can admin rollups run off the same computation, guaranteed not to drift?
  • Largest book size — decides live vs periodic rollup.
